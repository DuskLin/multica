[Project](/projects) resources tell agents which code this body of work uses and where to run. Resources stay linked to the project, so there is no need to re-paste repository URLs or local paths into every issue.

Two resource types are supported today:

| Resource | Best for | Where runs happen |
|---|---|---|
| **GitHub repository** | Code shared by the team, with checkouts managed by the runtime | A runtime-managed working directory |
| **Local directory** | An existing checkout, a very large repository, or when you want to inspect local changes directly | The original directory on a specific computer |

## How resources enter a run

When an agent works an issue inside the project, Multica adds the project name, project description, and resource list to the run's context, and writes `.multica/project/resources.json` into the working directory.

The workspace's linked repository list is always included in the run context. Repositories linked to the project additionally specify the code and default ref this body of work uses.

A local directory only applies to the daemon it is bound to. When the daemon executing a run has a matching local directory, the agent works directly in that directory; other computers keep using the project's GitHub repositories or the workspace repositories.

## Add a GitHub repository

Open the project and choose "Add resource" under **Resources**. Pick a repository already linked to the workspace, or paste a Git URL. Workspace repositories are managed in **Settings → Code**; once GitHub is connected, the same page offers **Pick from GitHub** to import repositories the App is authorized for.

Repositories are not limited to GitHub: any Git URL the runtime can reach works as a repository resource. Self-hosted Multica can also connect self-hosted Forgejo, Gitea, or GitLab under **Settings → Code**; see [Self-hosted Git hosting](/vcs-integration).

When creating a project, you can also pick repositories directly under **Repos**. One project can link multiple GitHub repositories.

A resource's `ref` sets the branch, tag, or commit that later checkouts use by default. `default_branch_hint` only gives the agent a default-branch hint and does not force a branch switch.

## Add a local directory

The UI for adding a local directory is Desktop-only, because browsers cannot pick folders on your computer.

<Callout type="warning">
**This is an escape hatch, not a more convenient default.** `local_directory` exists for people who have no other option — the canonical case is a game project whose checkout is tens of gigabytes, where re-cloning per run is simply not viable.

If your directory is an ordinary git repo you can clone, **use `github_repo` instead**: it uses worktree mode by default, allowing unlimited concurrent runs on the same repo. A `local_directory` processes **one run at a time by default**; if the directory is a git repo you can opt into worktree mode to get concurrency back (see "How runs share the directory"). Read "When to pick" below before you commit to it.
</Callout>


1. Make sure Desktop's local daemon is online.
2. Open the project's **Resources**, or the **Local directory** tab of the create-project dialog — the same choice is available before the project exists.
3. Choose "Add local directory", then pick the folder to use.
4. Pick how runs should use it — **Direct** or **Parallel**, described under "How runs share the directory". Desktop preselects **Parallel** when the folder is a git repository the runtime on that machine can isolate, and **Direct** otherwise. Change it right there, or later from **Resources** with the pencil next to the directory.

Preselection applies only to a directory you are linking now. A directory linked earlier keeps the mode it was saved with — an existing setup is never switched under you.

The directory must be an absolute path, must already exist, and must be readable and writable by the current daemon. These paths are rejected: system roots and drive roots (`/`, `C:\`), home directories themselves and the parents of home directories (such as `/Users`, `/home`, `/root`), and system directories such as `/etc`, `/var`, `/tmp`, `/usr`, and `/opt`. If the chosen path is a symlink, it is resolved to its real path first and validated again by the same rules; the serial lock also applies to the real path.

Each project can link at most one local directory per daemon. Different computers on a team can each link their own directory for the same project.

<Callout type="warning">
In the default `in_place` mode a local directory is not an isolated environment: the agent directly sees and modifies your current branch and uncommitted files, and Multica does not automatically switch branches, stash, commit, push, or open PRs. Worktree mode changes this — see "How runs share the directory" below.
</Callout>

## How runs share the directory

A local directory has two execution modes, set per resource with `execution_mode`. Desktop labels them **Direct** and **Parallel**; the API, the CLI and the rest of this page use the identifiers.

### `in_place` (default) — "Direct"

The agent works directly in your directory, and runs execute one at a time. When two runs use the same real directory, the later one enters `waiting_local_directory` and continues after the earlier one releases the directory. Two paths that reach the same directory through different symlinks serialize the same way.

Waiting does not modify the directory. A waiting run can be cancelled; otherwise it waits until the directory becomes available.

### `worktree` — "Parallel"

Each run gets its own [git worktree](https://git-scm.com/docs/git-worktree) of your repo, created inside the runtime's own workspace directory. **Runs on the same directory run concurrently — none of them wait**, and none of them write to your working copy.

Requires the directory to be a git repository with at least one commit. If it is not, runs fail with an explicit error rather than quietly falling back to serial execution. The runtime on that machine must also implement the mode. It declares that when it connects, and Multica gates on the declaration rather than on a version number — a development build can carry a version string that looks new enough while having none of the implementation. The declaration is checked twice: saving the resource is refused, with a hint to update the app on that machine, while its runtime does not declare the capability; and each run is checked again against the runtime that actually claims it — so a machine downgraded after the resource was saved has its runs cancelled with a reason instead of silently running them in place. Asking for `worktree` is asking for isolation; editing your working copy instead is never the fallback.

What the agent sees, and what you get back:

- **The agent starts from what you see, not from `HEAD`.** Your uncommitted edits and your untracked files are replayed into the worktree, so the agent is not reviewing code you no longer have. Your own working copy, index, and stash list are never touched. If that state cannot be reproduced faithfully — including when there is more untracked content than the replay covers (2000 files / 200 MiB) — the run fails instead of starting from a tree you would not recognise. The usual fix is to gitignore or clean up build output that is not already ignored.
- **The result is a branch in your repo**, one per issue rather than one per run: `agent/<agent>/<issue>` (a chat gets `agent/<agent>/chat-<session>`). The run's **Run details** panel shows the branch name (and lets you copy it); you can also find it with `git branch`. Review it with `git log` / `git diff`, and merge or cherry-pick it yourself. Multica never merges it for you. A run that failed partway still reports its branch, because it still committed whatever the agent had produced.
- **A follow-up continues where the last run stopped.** The next comment on the same issue checks that branch out again, so the agent is standing on the work it just delivered instead of starting from `HEAD` with its own changes stranded on another branch. Only what you changed in your own directory since the last run is replayed on top — the branch already carries the rest. Merge the branch and the next run starts from your `HEAD` again. If two runs on one issue overlap, the second one forks from the first's work onto `agent/<agent>/<issue>-<task>`, because git allows one worktree per branch.
- **Committed updates to your local `HEAD` are kept separate from uncommitted edits.** A pull or local commit between turns is not replayed onto the issue branch; merge those commits into it explicitly when needed. If the previous run captured uncommitted work, comparing it on the new `HEAD` requires Git 2.40 or later. If those older edits conflict with the new committed baseline, the runtime logs a warning and uses the current `HEAD` only for the affected paths; other drafts keep their incremental comparison. Finishing and committing one draft therefore does not block future runs or re-propose your unchanged drafts against the agent's work. Any conflict between your current edits and the agent's work is still offered to the agent to resolve.
- **If your edits collide with the agent's, the agent resolves them.** When you rewrite the same lines the agent rewrote, git cannot decide which version wins, so the run starts on a conflicted worktree and is told to finish the merge before anything else — `git status` in that worktree lists the unmerged paths. A run that leaves any file unmerged delivers nothing: it fails, keeps the worktree, and the next run offers the same edits again, so your change is never quietly dropped.
- **Only branches Multica owns are continued.** Continuing a branch is decided by an ownership record, not by its name: the record names the conversation, and it names the commit the branch was left at. A branch you created yourself that happens to be called `agent/<agent>/<issue>` is never checked out, appended to, or read as a previous run — and neither is one that no longer contains the recorded commit, so deleting Multica's branch and making your own under that name, or force-moving it onto other history, is safe. In those cases the run takes `agent/<agent>/<issue>-<id>` instead. Committing on top of a delivered branch is the normal case and keeps it continuing — your commit is simply there in the next run. Every branch also starts with a baseline commit of its own, marking the tree the first run began from — that commit is what identifies the branch later, and `git diff <baseline>..<branch>` is exactly the agent's work. A run that could not record its branch — it failed before finishing, the record could not be written, or it reset its worktree past the commit that carried your edits into the branch — reports failure and keeps its worktree, and later runs start a new branch rather than continuing one they cannot prove is theirs.
- **Nothing is silently dropped.** Anything the agent leaves uncommitted is committed to that branch before the worktree is removed, including when the run fails partway. In the rare case that commit itself cannot be made — for example a repo with `commit.gpgSign` and no signing key available to the runtime — the worktree is deliberately kept instead of removed, the run is reported as failed, and `git worktree list` in your repo points at the directory holding the work.
- **A run that changes nothing leaves nothing behind.** Its branch is deleted rather than left as an empty entry in `git branch` — unless it is the issue's branch carrying earlier runs' work, which always survives.

Because the worktree lives in the runtime's workspace directory, it is reclaimed on the normal cleanup schedule. Two things persist in your repo: the branch, and one hidden ref per branch under `refs/multica/local-state/` recording who owns it and what your directory looked like when it was last continued. The hidden refs never appear in `git branch`; list them with `git for-each-ref refs/multica`. Multica deletes each one with its branch, and drops any whose branch you deleted yourself the next time a run starts on that repo — or you can remove them at once with `git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d`.

<Callout type="warn">
**Self-hosted operators:** isolation for this mode is enforced by the server (at save time and again when a runtime claims each run), so a runtime downgraded at any point is caught. The combination that is *not* caught is rolling the server back to a build that predates this feature while runtimes that do not implement the mode are still connected — an old server has no gate, and such a runtime ignores `execution_mode` and would execute the run in place. Do not roll the server back past this release while `worktree` resources exist unless every runtime on those machines is up to date.
</Callout>

<Callout type="info">
Worktree mode covers git repositories. A non-Git directory can also run in parallel using script mode below.
</Callout>

### Parallel scripts (`script`)

Choose **Parallel · script** when creating a project or editing a local directory's execution mode. Set a `.sh` initializer path, absolute or relative to the linked project directory. Git is not required. The runtime machine needs Bash, and both the server and runtime must support script isolation.

The first run of an issue or chat creates an empty `<project>/.worktrees/multica-<kind>-<identity>` directory, then runs the initializer from the project directory:

```bash
bash -- /path/to/init-workspace.sh "$WORKTREE_DIR"
```

The destination is the first argument (`$1`), preserving spaces in paths. Write into that directory without replacing it or turning it into a symlink. When copying the source, exclude `.worktrees` to prevent recursive copies:

```bash
#!/usr/bin/env bash
set -euo pipefail
SOURCE_DIR="$(pwd)"
WORKTREE_DIR="${1:?Missing destination}"
rsync -a --exclude='.worktrees' --exclude='node_modules' \
  "$SOURCE_DIR/" "$WORKTREE_DIR/"
# Initialize dependencies or multiple repositories inside WORKTREE_DIR here.
```

The agent starts in the destination only after the script exits successfully. Initializer output is saved to `logs/init-workspace.log` in the run environment. A failed initializer stops the run and reports the log and preserved directory paths. Initialization shares the existing five-minute preparation deadline; cancellation or timeout terminates the preparation process and its children.

All runs of the same issue or chat, including follow-ups and retries by other agents, reuse one directory within the same workspace and source directory. Runs sharing it execute one at a time; unrelated conversations can run concurrently. An existing, successfully initialized directory is reused after runtime restarts without rerunning the script. Runs with no issue or chat use their own run identity. Run details points to this working directory. Multica does not automatically commit or merge modifications.

The runtime scans script directories on its existing GC schedule, **every two hours** by default (`MULTICA_GC_INTERVAL=2h`; `MULTICA_GC_ENABLED=false` disables it). An issue in the `done` lifecycle category is eligible without the ordinary environment retention delay. Reclamation requires an idle directory, clean repositories including untracked files, and an accessible remote branch containing every current local commit. If any subproject fails a check, the whole directory stays and the runtime logs the reason. Other branches and stashes in standalone clones, locked Git worktrees, and repositories needed by other worktrees are also checked. Cancelled/deleted issues, failed status lookups, standalone chats, and runs without an issue never authorize this reclamation.

Before removal, the runtime records each subproject's relative path, branch and remote identity in `.worktrees/.multica-script/`. It unregisters linked Git worktrees while retaining branches in the shared source repository. **This is reinitialization, not a file snapshot**: the initializer must recreate ignored dependencies, build outputs and configuration files.

Non-Git subprojects, files outside verified repositories, unpublished tags, index flags that hide modifications, and local "remotes" stored inside the deletion scope block reclamation. If Git or initializer process cleanup cannot be confirmed, a `.blocked` record quarantines the directory. Inspect remaining processes before manually removing that record to permit execution or collection again.

After an issue is reopened, its next execution reruns the `.sh` initializer and restores each recorded remote branch before starting the agent. Existing local branches are never forcibly reset. A missing remote branch, changed repository identity, branch conflict or recovery failure stops the run and preserves the partial directory. Inspect and move that directory before retrying, keeping its recovery record.

Ownership and initialization records live in `.worktrees/.multica-script/`. If initialization fails or is cancelled, the partial directory is preserved and retries stop rather than rerun the script over existing work. Inspect and move that directory before retrying to initialize it again. After upgrading, each source is registered when it first runs a script task; automatic GC still selects only issue-backed directories. Scans include existing directories with valid ownership in the same workspace. Legacy per-run directories without ownership records remain untouched. The script executes as the runtime user and is responsible for its copying, repository updates, and protection of the source directory.

Desktop **Settings → Work directories** combines ordinary managed directories and registered script directories across local profiles. It groups them by workspace and shows their size, associated task, and current status. Unavailable statuses remain unknown. Refresh scans again; Reclaim now queues the existing scheduled cleanup policy and reports removals, skips, and problems.

Deletion and reclamation run in the owning daemon's background queue. The confirmation closes after acceptance; search, task links, and submission of other directories remain available. Duplicate submissions reuse an active operation for the same target. The background cleanup section polls active operations every second and shows the stage, current repository, total elapsed time, stage elapsed time, and measured file/link removals where available. It does not estimate a percentage. Single-directory deletion measures only its target; confirmed completion updates the row before refreshing totals in the background.

Successful results without skips or problems move into the collapsed cleanup history after five seconds. Failures, skips, and problems remain visible until manually moved to history, where their details remain available. The background cleanup section disappears when no notices remain.

Leaving settings does not cancel cleanup. Returning shows daemon-held progress and results, with up to 128 records retained for the daemon's lifetime. Daemon shutdown interrupts operations; refresh the inventory after restarting to inspect the actual state. Interrupted deletion preserves recovery metadata and remaining content, and incomplete directories cannot resume execution.

Task links open verified issue details or chats and switch workspace when needed. Run directories use recorded issue/chat associations. Tasks on another server, deleted resources, and inaccessible resources do not receive links.

Individual deletion also permits unfinished tasks, after confirmation, but still refuses running directories, uncommitted files, unpublished commits, and repositories without verified remote recovery. Unknown files outside repositories, including results in `output/`, preserve the entire ordinary directory. Deletion does not change the task's status. Script directories retain their automatic restoration records. Ordinary directories retain a remote branch manifest under `.workdir-recovery/` in the runtime's workspace root for manual recovery; no file snapshot is saved.

Only the corresponding online daemon may perform cleanup or deletion. Offline and older daemons can still have their local directories listed, but must be started or updated before an operation. This page does not delete source project directories, directories with unverified ownership, or directories on other machines.

```bash
multica project resource add <project-id> \
  --type local_directory --local-path /path/to/project \
  --daemon-id <daemon-id> --execution-mode script \
  --init-script init-workspace.sh
multica project resource update <project-id> <resource-id> \
  --execution-mode script --init-script scripts/init-workspace.sh
```

## What gets written during a run

Beyond the code changes the agent makes, the runtime may also write into the directory the instruction files the current AI coding tool needs, plus `.multica/project/resources.json`. Add them to `.gitignore` if you do not want them under version control.

Multica never deletes a linked local directory when cleaning up run environments. The agent's changes to the directory are the same kind of changes as running an AI coding tool in your terminal yourself, and need the same review.

## Manage resources with the CLI

```bash
# Link a repository when creating a project
multica project create \
  --title "Agent UX" \
  --repo https://github.com/multica-ai/multica

# List and add resources
multica project resource list <project-id>
multica project resource add <project-id> \
  --type github_repo \
  --url https://github.com/multica-ai/multica \
  --ref main

# Link a local directory on a specific daemon
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id>

# Link a local git repo and let runs execute concurrently in their own worktrees
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id> \
  --execution-mode worktree

# Switch an existing local directory between modes
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place

# Remove a resource
multica project resource remove <project-id> <resource-id>
```

Resource changes affect runs created afterwards; they do not rewrite records of runs that already ended.
